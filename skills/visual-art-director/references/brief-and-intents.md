# Brief & intent routing

## Минимальный внутренний бриф

Собери из диалога и приложенных материалов, не переспрашивая известное:

- **Surface:** mobile screen / desktop screen / full flow / component / branding / existing Figma selection.
- **Task:** new design / redesign / visual exploration / typography / critique / Figma authoring.
- **User job:** что пользователь делает на экране, какой ключевой CTA.
- **Content:** реальные поля, навигация, состояния, цены, товары, названия; если не предоставлено — демонстрационные, не выдавать за реальные.
- **Audience & differentiation:** кому нужен продукт, за счёт чего отличается.
- **Constraints:** функциональные блоки, существующая система, логотип, разрешённая область изменений, accessibility.
- **Output:** images only / editable Figma / comparison / critique.

Если запрос «сделай современный дизайн магазина косметики» — достаточно информации для начала концепций: аудитория, устройство, сценарии могут быть приняты как гипотезы с пометкой. Вопрос обязателен только когда неизвестно, нужен ли вообще дизайн изображения или изменение конкретного Figma-файла (если эти выходы одинаково вероятны и последствия существенны).

## Design system intent — default locked

Существующий продукт, дизайн, Figma-файл, библиотека, бренд-гайд или отобранная ранее концепция автоматически включает `DS_LOCKED`; даже фразы «хочу вау», «экспериментально», «три версии» не разрешают менять утверждённые токены и компоненты. В режиме новой страницы существующего продукта сохраняй system baseline, допускай разные композиции/UX. Предлагай `DS_EXPLORATION` отдельно лишь если пользователь прямо просил новые темы, айдентику или изменения системы. При конфликте требования пользователя с существующим источником фиксируй точную коллизию и запрашивай решение, не угадывай.

Если нет доступа к Figma/библиотеке, не выдавай придуманную палитру и компоненты за фактические. Можно описать идеи в виде `DS_UNVERIFIED`, но полноценная compliant-запись требует реального source inventory.

## Параметры по умолчанию

- Язык интерфейса — язык пользователя, по умолчанию русский.
- Если не указано число — 3 варианта.
- При неопределённом устройстве — desktop для целой web-главной, mobile для явно мобильных задач. Для продукта с mobile-first контекстом приоритет mobile.
- При запросе redesign Figma-кадра — извлеки текущее содержание и ограничения до изменений.
- Размеры не жёсткие: подбирай по заданной платформе и существующему проекту. Для мобильного превью можно исходить из 390px ширины и проверить 360–430px.
- Отдельный концепт ≠ отдельная цветовая тема. Светлая и тёмная темы одной концепции считаются одной системой.
- Никакого самостоятельного бренд-ребрендинга без запроса.

## Сценарии и степень автономности

1. `explore`: исследование + разные изображения, **без Figma записи**.
2. `explore-and-figma`: исследование + выбранное направление → Figma; если пользователь не назвал вариант, можешь собрать три отдельных альтернативных фрейма, если ясно попросил несколько макетов именно в Figma. Иначе покажи и остановись на выборе.
3. `figma-only`: явный запрос «не делай картинки, сразу в Figma» → создавай нативный Figma дизайн с быстрым внутренним планированием; не трать бюджет на ImageGen интерфейса. Для фотографий и иллюстраций можно использовать image generation как источник ассетов.
4. `redesign`: сохраняй действия, ограничения, порядок критически важной информации; меняться могут композиция и визуальный стиль.
5. `typography`: чистая типографическая лаборатория с одинаковыми UI-текстами. При отсутствии imagegen можно дать обоснованные типографические спецификации, честно указав отсутствие визуальных образцов.
6. `audit`: только проверка и список замечаний с конкретными правками; без записи, если не просили исправлять.
7. `refine`: учитывай выбранный концепт, замечания пользователя, неизменяемые части. Избегай полного перезапуска дизайна без просьбы.

## Короткий формат для пользователя

Когда требуется показать гипотезы до генерации: максимум 3 строки о подходах, а затем визуальные изображения. Не выдавай многостраничное исследование, когда запрос был «сделай варианты».

## `Design.md` detection

If the existing project's design system is in `Design.md`, find and **read its actual full content** before proposing creative treatments. Follow `design-md-protocol.md`: extract all established tokens and patterns, inspect linked visuals, map components and states, and annotate open gaps. Do not require a published Figma library. An inaccessible expected file is a blocker for claims of design-system compliance, not an excuse to substitute generic components.
