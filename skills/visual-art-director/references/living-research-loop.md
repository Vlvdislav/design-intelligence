# Living Research Loop — ежедневное развитие без ложного «самообучения»

## Назначение

Этот документ позволяет отделять **ежедневные внешние находки** от **проверенных изменений скилла**. Исследование не меняет веса модели и не заменяет human review. Новая идея получает статус `candidate`; попасть в стабильную версию SKILL.md может только после регрессионных проверок.

## Два независимых потока

**Research track (daily, external scheduled task):**
1. Найти 2–4 свежих релевантных первоисточника, причём как минимум один источник о дизайне/взаимодействии и один — об UX/доступности/Figma, если действительно доступны.
2. Не переписывать вчерашнюю подборку: проверить реестр `research/ideas.json` при наличии доступа к нему. Если реестр недоступен, явно отметить `NO PERSISTENT LEDGER ACCESS` и сравнить с имеющимся контекстом; не обещать дедупликацию.
3. Для каждой находки зафиксировать фактическое поведение из источника, дату публикации (или `unknown`), URL, тип доказательства, типичный user task, предполагаемый механизм, пределы применимости, риски и контрпример.
4. Предложить не больше 3 атомарных изменений: точный файл, раздел, текст diff/patch, проверяемое ожидаемое поведение, affected modes и сложность.
5. Дать пример, на котором новое правило помогло бы, и пример, на котором оно ухудшило бы UX — контрпример обязателен.
6. Отмечать результат `research_only`, `candidate`, `tested`, `accepted`, `rejected`, `superseded`. Ежедневная выдача — **предложения**, не автоматическая установка на устройство пользователя.

**Release track (on explicit user approval or an available authorized repository workflow):**
1. Прочитать реальный текущий `SKILL.md` и refs из репозитория/архива (не полагаться на прошлую версию чата).
2. Выбрать только совместимые `candidate` с evidence: UX benefit, originality, repeatability, editable Figma feasibility, accessibility, regression cost.
3. Применить изменение в `references/` и при необходимости минимально обновить роутинг в `SKILL.md` (не раздувать основную инструкцию всеми трендами).
4. Запустить статическую валидацию, прогнать сценарии из `regression-scenarios.md`, выполнить хотя бы 1 живую визуальную проверку при наличии Figma access.
5. Сохранить changelog и резервную копию. Отчёт содержит `tested/not tested`, список изменённых файлов и реальные ссылки/пути. Никогда не заявлять, что локальная установка обновлена, если запись на неё не выполнялась.

## Шаблон дневного отчёта

**Дата/контекст**, **2–4 прямых источника** (даты и статус просмотра), **независимое наблюдение**, **прикладной UX-смысл**, **1–3 конкретных proposed patches**, **контрпример**, **проверка на Fresska/KAIRN/VELL**, **что не принимаем и почему**, **что потребуется для внедрения**.

Важно: непроверенные demos с визуальным wow нельзя выдавать за доказательство конверсии. Изменения MCP API нужно перепроверять по официальной документации в каждый релиз, а не консервировать случайные версии/названия инструментов в коде скилла.

## Design quality guard для ежедневной находки

Отклонить идею, если она:
- добавляет эффект без задачи и альтернативы для touch/reduced-motion;
- превращает свободный discovery hero в обязательный 3D-путь к каталогу;
- нарушает Figma-first и требует production frontend на этапе концепций;
- не отличает «сильный визуал» от изменения в UX;
- копирует layout/бренд чужого примера или не содержит provenance;
- ориентируется на один красивый screenshot без доказательства состояния, переходов и состава макета;
- расширяет SKILL.md без объяснения, почему существующего правила недостаточно.

## Передача в автоматизацию

Автоматизация ChatGPT и локальная папка Codex — разные среды. Не рассчитывай на автоматический доступ к `~/.agents/skills`, даже если в текущем чате можно читать ZIP. Для действительно автоприменяемых патчей потребуется выбранный пользователем постоянный репозиторий с правами записи, ревью/approval и отдельной проверкой перед публикацией.
